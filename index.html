Official Standard Operating Procedure

AI-Assisted Figma to WordPress Development

This document outlines the step-by-step workflow for translating Figma designs into production-ready WordPress sites using AI tooling, Model Context Protocol (MCP) integrations, and developer guardrails.

1 Stage 1: Local Environment Setup

1.1 Local WordPress Setup

  • Spin up local WordPress site (e.g., LocalWP, Lando, or DDEV).
  • Configure environment details: PHP Version 8.2+, NGINX / Apache, WP Version (Latest Stable).
  • Install base theme framework (Custom Starter / Block Theme) and essential plugin stack.

1.2 Version Control Initialization

  • Initialize Git repository in the custom theme or project root: git init
  • Create .gitignore (exclude wp-config.php, uploads/, node_modules, vendor files).
  • Set up default branching structure: main (Production), staging (Testing), feature/[section-name] (Working branches).

2 Stage 2: AI Tooling & MCP Integration

2.1 IDE Setup: Open local project directory in Claude Code / terminal IDE and verify permissions.

2.2 WordPress MCP Connection: Connect WordPress MCP server (Novamira WP MCP) via Application Passwords or API keys in .env. Validate CRUD access to posts, CPTs, fields, and options tables.

2.3 WordPress Agent Skills: Install and verify agent skills for Template hierarchy lookup, Block / ACF field definitions, and Code linting & security validation.

2.4 Browser & Figma Connectors: Connect Claude Chrome extension for active DOM inspecting and visual checking, and Claude Figma MCP integration for direct component inspection.

3 Stage 3: AI Guardrails & Context Rules

Create a CLAUDE.md file in the project root to enforce coding standards, directory conventions, and security guidelines:

# Project Guardrails & Rules

## WordPress & PHP Standards
- Follow WordPress Coding Standards (WPCS).
- Always sanitize inputs (`sanitize_text_field`, etc.) and escape outputs (`esc_html`, `esc_attr`, `esc_url`).
- Use strict typing where applicable (`declare(strict_types=1);`).
- Do not edit core files or third-party plugin source code directly.

## Architecture Guidelines
- Keep logic separate from presentation (utilize render templates or controllers).
- Use `theme.json` or standard CSS variables for styling consistency.
- Avoid inline styles; utilize utility classes or styled CSS components.

## AI Assistant Behavior
- Execute edits incrementally, section by section.
- Run syntax and lint checks prior to marking tasks as complete.
- Prompt for human confirmation before running database-altering commands or destructive file operations.

4 Stage 4: Figma Design Analysis & Tokenization

4.1 Permissions & Seat Audit: Determine whether using Free / Collab Seat (manual visual comparison, Dev Mode screenshots) or Dev / Full Seat (Figma MCP context, variable trees, auto-layout tokens).

4.2 Design System & Token Extraction: Extract Color Palette, Typography Scale (clamp() font sizes), Spacing Grid system (4px/8px scale), and Box Shadows into theme.json or CSS custom properties.

4.3 Breakpoint Definition: Mobile (375px–639px), Tablet (640px–1023px), Desktop (1024px–1439px), Wide Desktop (1440px+).

5 Stage 5: Architecture & Development Plan

5.1 Global Components: Map out Headers (sticky/transparent), Mobile Navigation Drawers, Footers, and CTA Banners.

5.2 Content Model: Define CPTs, Taxonomies, and ACF / Meta field structures (Field keys, Flexible Content vs Repeater).

5.3 Section Execution Plan: Enter Claude Plan Mode to draft a modular section roadmap with priorities and dependencies.

  • 6.1 Develop Section: Write markup (PHP/HTML), styles (CSS/Tailwind), JS, and bind ACF variables.
  • 6.2 Visual Diff vs Figma: Verify typography, spacing, padding, and hover states across responsive viewports.
  • 6.3 Frontend & Backend Review: Check HTML semantics, output escaping, and block editor preview render.
  • 6.4 Commit Work: Git commit with descriptive section scope: git commit -m "feat(hero-section): implement hero banner"

7 Stage 7: Quality Assurance & Testing

  • Cross-Device & Responsive testing (320px to 2560px).
  • WCAG AA accessibility check (contrast, keyboard nav, screen reader labels).
  • Performance & Core Web Vitals (LCP < 2.5s, CLS < 0.1).
  • Cross-browser testing (Chrome, Safari, Firefox, Edge).

8 Stage 8: Content & SEO Preparation

  • Replace lorem ipsum with production client copy & WebP media.
  • Configure meta titles, descriptions, and OpenGraph tags.
  • Set up XML sitemaps, canonical URLs, and Schema.org JSON-LD.

9 Stage 9: Deployment & Client Handoff

  • Deploy local build to public Staging environment.
  • Migrate database and perform URL search-and-replace.
  • Execute final client visual diff review & receive sign-off.

10 Stage 10: Production Launch

  • Backup existing target server database & files.
  • Execute DNS cutover and verify Let's Encrypt / SSL.
  • Enable search engine indexing & server page caching.
  • Post-launch audit: GSC sitemap, forms, analytics tracking.
